# Spike M7 — one remote relay-tty session through relaytty.com

**Question** (Phase 0 of [`docs/plans/remote-relay-servers.md`](../plans/remote-relay-servers.md)):
does the app's own `RelaySession` work over a WebSocket through the
relaytty.com tunnel, byte for byte and fast enough to feel like a local lane,
and what does auth actually look like on that wire?

**Verdict: GO for Phase 1, with Phase 0b in front of it.** The transport is
byte-exact through the tunnel (100 001 lines, three paths, one sha256, equal
to the ground truth), a keystroke echoes in **25 ms median / 39 ms p95**
against **0.5 / 0.6 ms** on a local Unix socket, `RESUME` reaches pty-host
inside its 100 ms window on a fresh attach, and `RelaySession.handle` was not
touched. Two things would make a remote lane behave visibly unlike a local
one, and both are relay-tty's to fix (§9): the tunnel accepts a session
WebSocket **with no credential at all** (§4), and a reconnect after an outage
gets a **full replay disguised as a delta** (§3), which the app can at least
detect.

Report path: `docs/spikes/07-m7-remote-relay.md`. Program: `spikes/m7-remote-relay/`
(`README.md` there says how to re-run; raw runs are under its `out/`).

### What was built

- **`RelayTransport`**, a protocol with `open(firstPayload:)`, `send`, `close`,
  `onPayload(type, body)` and `onClosed(RelayClose)`. A payload is `[type][data]`
  and nothing else.
- **`UnixSocketTransport`**: `RelaySession.connect()` and `drain()` as they
  were, moved; adds the 4-byte length and parses it off (`FrameParser`).
- **`WebSocketTransport`**: `URLSessionWebSocketTask`; one binary message is one
  payload, no prefix either way; text frames counted and dropped; `PING` (0x20)
  every 10 s, no inbound frame of any kind for 45 s is a zombie; WS close 4001
  and 1008 are `RelayClose.isFinal`. The first payload is queued on the task
  before the 101, so it is first on the wire after it. The credential rides as
  `Cookie: session=…` on the upgrade, or as `?token=` when asked, so both could
  be measured.
- **`RelaySession`** takes a transport (default: Unix, so nothing changes for
  the app). `handle` is byte for byte what it was — `git diff` of the file
  touches nothing below `private func handle`. It gained `closeReason` and an
  `onPayload` tap the bench uses for `SESSION_UPDATE`.
- **`RelayAttachmentAdapter`** takes a transport factory and **stops
  reconnecting on a final close** (`RelayTransportTests`, "a refused credential
  stops the adapter reconnecting").
- **`MAXPANE_SPIKE_REMOTE`** (`SpikeRemote.swift`): read from the environment
  only; with it unset the shipped app reaches none of this. With it set, the
  named session gets a lane at the end of the strip and that pane attaches over
  the WebSocket transport. `build/spike.app` was built for the owner (§10).
- **`RelayTransportTests`**: ten tests against a Network.framework WebSocket
  server on a loopback port: `RESUME` leaves as 17 bytes with byte 0 the type
  (the Unix wrapper of the same bytes is 21); inbound `RESIZE`/`SYNC` complete
  the handshake unprefixed; input is `[0x00][bytes]`; two text frames are
  dropped and counted with the binary after them still landing; PING cadence
  and PONG count; zombie after `zombieAfter` and it is retryable; 4001 and 1008
  final, 1000 not; cookie vs query URL; the adapter's stop; the env var's
  parser. 2.4 s, in the default run.

## 1. Byte-exactness

Session `52153adf` on the box: `bash -lc 'read -r x; seq 1 100000; sleep 1800'`.
Three clients attached with the replay clamped to 1 byte, the tunnel client
typed `\r`, and each hashed every `DATA` byte for 40 s. Ground truth is
`"\r\n"` (the echoed Enter) plus `seq 1 100000` with the PTY's `ONLCR`:
**688 897 bytes, 100 001 lines, sha256 `cb6eff97…78399a`**.

| path | client | DATA bytes | frames | sha256 | final offset | server `totalBytesWritten` |
|---|---|---|---|---|---|---|
| tunnel (Mac → relaytty.com → box) | `m7 stream` | 688 897 | 56 | `cb6eff97…78399a` | 688 897 | 688 897 |
| ssh `-L` forward (Mac → box loopback) | `m7 stream` | 688 897 | 56 | `cb6eff97…78399a` | 688 897 | 688 897 |
| Unix socket, on the box | `tap.mjs stream` | 688 897 | 56 | `cb6eff97…78399a` | 688 897 | 688 897 |

Then a fresh, unclamped `RESUME(0)` against the same session on each path:

| path | replay plain | on the wire | gz | lines | sha256 | handshake |
|---|---|---|---|---|---|---|
| tunnel | 688 897 | 198 789 | yes | 100 001 | `cb6eff97…78399a` | 221 ms |
| ssh forward | 688 897 | 198 789 | yes | 100 001 | `cb6eff97…78399a` | 227 ms |
| Unix socket, on the box | 688 897 | 198 789 | yes | 100 001 | `cb6eff97…78399a` | 9.5 ms |

Live stream and replay are identical to each other and to the ground truth on
every path. **Zero bytes lost, zero frames reordered, zero desynchronisation.**
The tunnel delivered the 56 live frames in a 56 ms span (the ssh forward took
337 ms: sshd's own buffering, not the protocol).

## 2. Keystroke latency

A session running `cat` (the tty echoes the byte before `cat` reads it, so this
is the transport and pty-host and nothing else). One byte, wait for the `DATA`
carrying it, 100 ms gap, **n = 200 on every path, 0 lost**.

| path | client | min | **p50** | p90 | **p95** | p99 | max |
|---|---|---|---|---|---|---|---|
| **tunnel**: Mac → relaytty.com → box | `m7` (the app's transport) | 17.4 | **25.2** | 34.6 | **38.6** | 48.4 | 60.0 |
| ssh `-L` forward: Mac → sshd → box loopback | `m7` | 13.2 | **19.6** | 34.3 | **37.9** | 58.4 | 171.7 |
| LAN address, from the box itself (`192.168.68.56:44936`, cookie) | `tap.mjs` | 0.51 | **1.31** | 2.06 | **2.19** | 2.32 | 2.61 |
| loopback WebSocket, on the box | `tap.mjs` | 0.62 | **1.80** | 2.67 | **2.88** | 3.11 | 3.35 |
| Unix socket, on the box | `tap.mjs` | 0.20 | **0.74** | 1.13 | **1.31** | 1.68 | 3.18 |
| **local**: Unix socket on this Mac (`relay-pty-host` 1.23.0, `bash -lc cat`) | `m7` (the app's transport) | 0.21 | **0.50** | 0.61 | **0.63** | 0.75 | 1.02 |

Read: the WebSocket bridge itself costs about **1 ms** over the Unix socket on
the same machine (0.74 → 1.80 p50); everything above that is the network. The
tunnel's 25 ms median is the Mac → Cloudflare → box → back path (TCP connect
to the edge alone is 35 ms round trip, so the edge is doing well by us). The
ssh forward, which rides a different cloudflared tunnel, is 6 ms faster at the
median and worse at the tail. A true LAN-direct run from this Mac could not be
done (§11); the box-to-its-own-LAN-address run is the control for the auth
path (§4) and for the bridge's cost, not for a wire.

For the pane this means: typing over the tunnel is under a frame and a half
at 60 Hz at the median and under three at p95; M2 measured SwiftTerm's local
echo at 0.33 / 3.4 ms. The difference is felt as "remote", not as "broken".

## 3. Reconnect

The Mac cannot lose its network without the owner losing his, and it was in
use, so the outage was made at the far end: `kill -STOP` on the relay server
process (which holds both the tunnel WebSocket and the loopback bridge) for
**10 s, 60 s and 180 s**, `kill -CONT` between, while `m7 reconnect` ran the
adapter's exact policy through the tunnel against session `0368d543` (`date`
every 30 s): resume from the last offset, 0.5 s → 15 s backoff, stop on a
final close. From the client's side a frozen server is a dropped network: no
FIN, no RST, silence. The differences from a real drop are in §11.

| outage | what the transport saw | reconnect | replay after |
|---|---|---|---|
| **10 s** (t = 25.7–34.5 s) | One PONG missing. No close. The next `date` line (t = 42.2 s) arrived on time. Had a line fallen inside the window it would have arrived at CONT, buffered, not lost | none needed | — |
| **60 s** (t = 92–149.5 s) | Silence; **zombie at t = 140.1 s**, 45 s after the last inbound frame (`pings=13 pongs=9`). Reconnect 0.5 s later while the server was still frozen: the edge answered 101 at once and then nothing; handshake completed at t = 150.0 s, 0.5 s after CONT | attempt 2, from offset 2 518 | **2 578 B, the whole ring**, `SYNC 2578`, flagged `delta` by the client. The two lines printed during the freeze (22:22:46, 22:23:15) were in it — nothing lost — but so were the 2 518 bytes the client already had |
| **180 s** (t = 222–395 s) | Zombie at t = 270.7 s; attempts 3 and 4 each hung 50 s on an edge that said 101 and sent nothing, then zombied (`pings=4 pongs=0`); attempt 5 (backoff 2 s) handshook at t = 395.1 s, 0.4 s after CONT | attempt 5, from offset 2 668 | **2 848 B, the whole ring**, `SYNC 2848`, again flagged `delta`. Every line from the freeze present; every earlier byte repeated |

Offsets stayed right throughout (`SYNC` is absolute, §3.4 of the reference),
and live `DATA` resumed within a second of the server coming back. The wrong
thing is the shape of the replay, and it is not the transport's doing:

**A `RESUME` that reaches the box while its bridge is still opening is
dropped.** `tunnel-client.ts` handles `CLIENT_OPEN` by starting a local
WebSocket and only registers it on `"open"` (`handleClientOpen`, `:257-258`);
a `DATA` frame for that client that arrives before then is discarded
(`handleWsData`, `:283-286`: `if (localWs && localWs.readyState === WebSocket.OPEN)`). After a
freeze the edge has both frames queued back to back, so the `RESUME` is lost,
pty-host's 100 ms window expires, and it sends a **full replay with no
`SYNC(0)` cache reset** (`send_full_replay`, `main.rs:2581`; the reset is only
sent on the "offset too old" path, `:2559`). The client captured `isDelta`
from its own offset, as the reference says to, and had no way to know.
On a fresh attach the race is not hit: the client's `RESUME` follows its own
101 by a full Mac round trip, which is 25 ms the bridge does not need — the
clamp landing in every §4 probe (90 B of a 1 588 B ring) is the proof that
`RESUME` normally arrives in time.

What the pane would show: during the freeze, nothing new and no banner for
45 s, then the reconnecting state; after it, the whole scrollback appended
again. **Client-side detection is possible today**: a replay flagged delta
whose length equals the `SYNC` value that follows it (and exceeds
`SYNC − offset`) is a full replay; the adapter can clear the emulator before
feeding it. That is a Phase 1 line with a test, not a workaround for the
tunnel-client bug, which stays in the ticket (§9).

**Sleep/wake**: not run (§11). `WebSocketTransport.pingNow()` exists for the
`NSWorkspace.didWakeNotification` hook; the app does not call it yet.

**The tunnel itself dies quietly.** Before any of this, the tunnel set up at
21:42 was found dead at 22:05: the box's TCP socket to the edge was `ESTAB`,
`GET /api/sessions` through the edge hung for the full 15 s timeout with no
error and nothing reached the server log, and a WebSocket upgrade got a 101
and then silence. Neither end keeps the tunnel alive: `tunnel-client.ts`
answers protocol pings (`:133`) that the Durable Object does not send, and the
DO auto-answers a text `"ping"` (`tunnel-relay.ts:68`) that the client never
sends. A restart fixed it. This is the same failure a remote lane will meet on
the road, and the app's only defence is the 45 s zombie, which then reconnects
into an edge that says 101 and means nothing.

## 4. Auth, on the wire

Session WebSocket `/ws/sessions/0368d543`, `RESUME(0, 100)`; "handshake" means
`RESIZE`, a 90-byte clamped `BUFFER_REPLAY`, `SYNC`, `SESSION_STATE` all
arrived. Through the tunnel the edge completes every upgrade with 101 before
the box is involved, so the status column is the local server's answer as the
tunnel client saw it.

| credential on the upgrade | **through the tunnel** (from the Mac) | **LAN-direct** (box → its own `192.168.68.56:44936`) |
|---|---|---|
| right `Cookie: session=<jwt>` | handshake, replay, 216 ms | handshake, replay, 12 ms |
| **no credential at all** | **handshake, replay, 143 ms** | **`HTTP/1.1 401 Unauthorized`**, socket destroyed |
| wrong cookie (`eyJ….WRONG.WRONG`) | **handshake, replay, 177 ms** | `HTTP/1.1 401 Unauthorized` |
| right token as `?token=` | handshake, replay, 153 ms (same as none) | `HTTP/1.1 401 Unauthorized` |
| wrong token as `?token=` | handshake, replay, 147 ms (same as none) | `HTTP/1.1 401 Unauthorized` |
| no credential, bogus session id | close 1000 "Session closed" (the bridge's `socket.destroy()`, relayed) | — |
| loopback on the box, no credential | — | handshake (the documented localhost bypass) |

Facts, with the evidence:

1. **Through relaytty.com, `/ws/sessions/:id` accepts a connection with no
   cookie, with a wrong cookie, and ignores `?token=` either way.** Evidence:
   the five rows above, each with the session's replay bytes in hand
   (`spikes/m7-remote-relay/out/auth/tunnel.txt`, JSON beside it); and on the
   box during a credential-less tunnel attach, `ss -tnp` shows the server's
   peer as `127.0.0.1:47049` from the `relay` CLI process (pid 2839, which runs the tunnel client; the server is its child, 2848)
   (`out/auth/tunnel-none-ss.txt`). The server's code takes that peer as local
   and returns before reading any header (`verifyWsAuth`, `auth.ts:426-428`),
   and the tunnel client sends the WebSocket upgrade with the path and no
   headers at all, by its own comment (`tunnel-client.ts:248-253`). The edge
   *does* forward the query string in `CLIENT_OPEN` (`tunnel-relay.ts:149`,
   "forward query string in WS path", commit `635e8ea`), so `?token=` reaches
   the box today and is simply not read.
2. **LAN-direct, the cookie is required and is the only thing that works.**
   Evidence: `HTTP/1.1 401 Unauthorized` written on the upgrade for none, wrong
   cookie, and both `?token=` forms (`server.js:179`), and a handshake with
   the right cookie (`out/auth/lan.txt`). `?token=` is read for `/ws/share`
   only (`ws-handler.ts:201`).
3. **HTTP through the tunnel is authenticated** (401 / 200, §Environment), so
   the plan's sentence stands exactly: over the tunnel, HTTP is authenticated
   and WebSocket is not.

Consequence for the app: with this server, **anyone who knows the slug and an
eight-hex session id can read and type into that session through
relaytty.com**, and Phase 1 must not ship a tunnelled remote lane to a
travelling build until Phase 0b lands (§9).

## 5. Agent state and cwd

**Cwd**: no OSC 7 anywhere. `bash` on the box (Ubuntu's default, no shell
integration) emits none; a 60 s `watch` of a fresh attach and every replay
scanned found zero `ESC ] 7 ;` sequences. Cwd arrives only inside
`SESSION_UPDATE` (`cwd=/home/spierce`, `cwd=/home/spierce/m7out` in every
update below), which pty-host fills from `/proc/<pid>/cwd` on its 5 s poll.
So for a remote session the answer to "does OSC 7 give cwd sooner" is: only
if the remote shell is configured to send it, which this one is not.

**`SESSION_UPDATE` on a fresh attach**: none for the attached session. In 11
attaches to the fake agent, the only updates before anything was typed were
for *other* sessions (two, at +748 ms and +830 ms, for `2a462b22` and
`0368d543`), which is the documented broadcast-to-everyone (§2 of the
reference; filter on `id`). A session that is already BLOCKED when the pane
attaches will never say so over the WebSocket; the sidebar has to ask
`GET /api/sessions/:id`, which is **~200 ms through the tunnel** (three
samples: 201, 182, 463 ms). The plan's ask 5.2 (send `SESSION_UPDATE` once on
attach) is what would make it 0 ms.

**Time from the prompt appearing to `SESSION_UPDATE agentState=blocked`**,
through the tunnel. A `cat` copied to `~/m7out/claude` and run as
`bash -li -c "/home/spierce/m7out/claude; exit $?"` — the no-`exec` wrapper the
app uses locally, so `foregroundProcess` is `claude` and the classifier's
first rule passes — typed `Do you want to proceed?\r` (the pattern lands in
the 4 KiB tail through the tty echo), and 4 260 bytes of filler to push it out
again:

| transition | n | samples (ms, keystroke sent → update received) | median |
|---|---|---|---|
| → **blocked** | 6 | 820, 953, 1 129, 316, 512, 622 | **721** |
| → working | 5 | 400, 559, 715, 878, 1 026 | **715** |

That is the 1 s classifier tick + the session-file write + the server's
200 ms `fs.watch` debounce + one tunnel hop, and it is the same path a local
sidebar reads off the disk minus the hop. A remote BLOCKED would pulse within
about a second of the prompt, like a local one.

**Real Claude Code**: spawned the same way in `/home/spierce/m7out`
(`foregroundProcess: claude`, title `✳ Claude Code`, updates flowing:
`working` at +1.07 s of attach, then on each spinner-title change). Two things
stopped the measurement short of a real permission prompt: the box's Claude
login has expired (`API Error: 401 OAuth access token has expired`, on the
screen after the first prompt) and its config has auto mode on, which would
not ask anyway. Both are the owner's to change; the fake-agent numbers above
exercise the same classifier and the same wire. One classifier finding on the
way: the trust-folder prompt (`❯ 1. Yes, I trust this folder`) was reported
`working`, not `blocked`, because Claude Code draws it with cursor moves
between the glyphs and `strip_ansi` leaves `❯1.Yes`, which `"❯ 1. Yes"` does
not match. That is a relay-tty note, not an app bug.

## 7. Handshake cost through the tunnel

From `connect()` to `SYNC`, fresh attaches:

| case | 101 seen | first frame | `SYNC` | replay on the wire |
|---|---|---|---|---|
| 1.6 KB ring, clamped to 100 B | 121 ms | 143 ms | 143–216 ms | 90 B plain |
| 689 KB ring, unclamped | 121 ms | 149 ms | **221 ms** | 198 789 B gz |
| the same over the ssh forward | 70 ms | 94 ms | 227 ms | 198 789 B gz |
| the same on the box's Unix socket | 1.7 ms | — | 9.5 ms | 198 789 B gz |

`RESUME` left the client 0.6–1.0 ms after `connect()`, queued ahead of the
upgrade, and the clamp was honoured in every fresh attach: through the tunnel
pty-host's 100 ms window is met. A 10 MiB ring would be about 15× the gz
bytes above; the app clamps cold attaches to 256 KiB already.

## 8. Memory and process cost

`phys_footprint` of the spike process (`proc_pid_rusage`): **4.7 MB** before
any attach, **5.9 MB** holding a tunnel attach after 689 KB of `DATA`, **7.7 MB**
after inflating the 689 KB replay. `URLSession` and its one connection are
about a megabyte; there is no `WebContent` process, no second `Networking`
process, and the emulator is the same libghostty grid a local lane has.

## 9. What Phase 0b must change upstream (the relay-tty ticket)

In order of necessity. 1 and 2 are the gate for a travelling build; 3 is what
makes a reconnect look local; 4 and 5 are what this spike found on the way.

1. **`verifyWsAuth` reads `?token=` on `/ws/sessions/:id` and `/ws/events`.**
   `server/auth.ts:421`: after the cookie check, parse `req.url` and accept a
   `token` query value that `verifyJwt` accepts as an owner JWT (the same
   shape `/ws/share` takes at `ws-handler.ts:201`, but verified as the owner's
   `session` token, not a share token). A guest grant stays cookie-only.
2. **The tunnel client marks its WebSocket upgrades as tunnelled.** In
   `handleClientOpen` (`tunnel-client.ts:246`), open the local WebSocket with
   `headers: { "x-relay-tunnel": "1" }` so `verifyWsAuth`'s `isRelayTunnel`
   revokes the localhost bypass, exactly as `x-relay-tunnel` already does for
   HTTP (`:184-188`). The comment at `:248-253` says this was left out because
   nothing carried a credential; with 1 in place `?token=` does, and the
   web app must then append it too — `app/lib/browser-stream.ts:37`
   `wsUrlForPath` needs the token, which means the server exposing the
   session JWT to the page (it is an httpOnly cookie today) or the edge
   forwarding the `Cookie` header in `CLIENT_OPEN` (`tunnel-relay.ts:149`
   builds the payload from `url.pathname + url.search` only). The edge change
   is the smaller one and keeps the web app untouched: put the browser's
   `Cookie` header in the `CLIENT_OPEN` payload, and have `handleClientOpen`
   pass it as an upgrade header. Either way, **with 2 and not 1, every
   tunnelled session WebSocket is refused, the web app included** — ship them
   together.
3. **`handleClientOpen` queues `DATA` frames until the local WebSocket is
   open** (`tunnel-client.ts:257-286`): buffer per `clientId` until `"open"`,
   then flush in order. Today a `RESUME` that arrives before the local
   bridge is open is dropped, pty-host's 100 ms window expires, and the
   client gets a full replay it cannot tell from a delta (§3). Independently,
   **pty-host sends `SYNC(0)` before every full replay to a client whose
   `RESUME` carried an offset > 0**, not only on the "offset too old" path
   (`main.rs:2559` vs `:2581`), so a client can always tell.
4. **Keep the tunnel alive.** `tunnel-client.ts` sends the text `"ping"` the
   Durable Object already answers (`tunnel-relay.ts:68`) every 30 s, and
   treats no `"pong"` within 90 s as a dead tunnel: close and reconnect. Today
   a silently dropped tunnel stays `ESTAB` on the box forever and the public
   URL hangs (§3, last paragraph).
5. **`SESSION_UPDATE` once on attach** (plan §5.2), so a remote pane learns
   `agentState`, `cwd` and `title` in the handshake instead of on the next
   change, and the sidebar does not need `GET /api/sessions/:id` per lane.

Also noted, not gating: the classifier misses Claude Code's trust prompt
(§5); the edge relays a bridge-side `socket.destroy()` as close 1000
"Session closed" rather than 4004, so "no such session" is not
distinguishable from "connection dropped" through the tunnel; and after the
freezes, **four loopback bridge connections** (tunnel client ↔ server, each
holding a pty-host client) were still `ESTAB` with no remote client behind
them, 30 s and more after every client of this spike had gone — the
`CLIENT_CLOSE` for a client that left during a stall does not seem to reach
`handleClientClose`, and each leaked bridge counts as an attached client for
the classifier's Done → Idle rule.

## 10. Go/no-go for Phase 1, and the feel

**Go.** Nothing in the measurements needs the app to do anything differently
for a remote session than for a local one, except where relay-tty makes it
(§9). Against the rule that a remote session must feel like a local lane with
one simple mark:

| would a remote lane behave visibly differently? | measured | verdict |
|---|---|---|
| Bytes on screen | identical, 100 001 lines, every path | no |
| Typing | 25 ms median through the tunnel vs 0.5 ms local | felt as distance, not as lag; no |
| Attach | 143–221 ms to `SYNC` vs 9.5 ms; the clamp works | a blink; no |
| Paste | whole at 64 KiB | no |
| BLOCKED | ~0.7 s after the prompt, same as local minus the hop | no — **if** the sidebar also asks the server once on attach, or 0b-5 lands |
| cwd | from `SESSION_UPDATE` only, 5 s poll, no OSC 7 | same as a local `bash` without integration; no |
| A dropped connection | 45 s of silence before the banner; then a full replay appended | **yes**, twice — the banner delay is the zombie policy (a `PING` on wake and on network change would shorten it), the replay is 0b-3, detectable client-side meanwhile |
| Who can attach | anyone with the slug and the id, through the tunnel | **yes**, and not visible at all — 0b-1/2 before a travelling build |

Phase 1 can start on the transport and tests as they are. It should add: the
full-replay-as-delta detection; `pingNow()` on `didWakeNotification` and on

## 11. Not measured, and why

- **LAN-direct from this Mac.** The Mac was not on the box's LAN (owner
  travelling; `192.168.68.10` unreachable). The control was run from the box
  against its own non-loopback address, which exercises the same
  `verifyWsAuth` path and the bridge, but not a wire.
- **A real network drop on the Mac, and sleep/wake.** Both would have taken
  the owner's network or his session; the server was frozen instead (§3).
  What a real drop adds: `URLSession` may report
  `NSURLErrorNetworkConnectionLost` at once instead of 45 s of silence (the
  easy case, a retry), and after a wake the first sign is the same silence
  until `pingNow()` is wired.
- **A real Claude Code permission prompt.** The box's Claude login has expired
  and its config auto-approves (§5); the fake agent stands in for the
  classifier path.
- **A web lane control.** Removed from the brief by the owner on 2026-09-17;
  the comparison with the web app is feature for feature in the plan's §0.
- **The lane in the running app.** `build/spike.app` was built and not
  launched, by the rules. To run it, from a terminal of his own, with the
  token read the way the task file says:

  ```sh
  MAXPANE_SPIKE_REMOTE="https://yourslug.relaytty.com|0368d543|$(ssh yorkshire-wsl 'grep -o "callback?token=[A-Za-z0-9._-]*" ~/relay-server.log | tail -1 | cut -d= -f2')" \
    MAXPANE_WINDOWED=1 build/spike.app/Contents/MacOS/MaxPane --profile spike
  ```

  The session gets a lane at the end of the strip; it renders, resizes and
  takes input through the transport measured here. Note the token is the one
  after the restart in §3; an earlier one is refused on HTTP and, through the
  tunnel, ignored on the WebSocket (§4).

## 12. Safety

The owner's eight local sessions were never touched: the local control ran
`relay-pty-host` under `HOME=/tmp/m7h` (its socket path has to be short), and
that directory and host were removed afterwards. On the box, the spike spawned
its own sessions through `POST /api/sessions` and stopped them at the end,
leaving `0368d543` running as found. The one intervention on the box was the
server restart in §3, in its tmux session, after the tunnel had died on its
own; the token changed with it and the task file's instruction (read the last
`Auth URL` line) still finds it.
